**Fix 2 — conversion shrinkage phantom.** User saw "0.50 BBL available in brite" after fully packaging B-038. Root cause: B-038 was conversion-born from parent `eb5b0b93` — the conversion transfer delivered 24.5 BBL + 0.5 shrinkage, so only 24.5 physically arrived, but the pre-planned target kept `volume_bbl`=`converted_volume_bbl`=25. `computeLocationBreakdown` (lib/production/volumeLedger.ts) correctly seeds a conversion-born batch from the DELIVERED inflow (24.5, NOT the nominal — inbound shrinkage is the SOURCE's loss), so accountedFor=24.5 but the card compares vs originalVol=volume_bbl=25 → permanent 0.50 `⚠ unbalanced` (BatchLogTab balanced threshold = |accountedFor-originalVol|<0.01). Brite itself nets to ~0 (dust-filtered), NOT 0.5 — the 0.5 is the gap, not liquid. Migration `20260808_reconcile_b038_converted_volume.sql` sets volume_bbl/converted_volume_bbl=24.5 (guarded on stale 25,25). **APPLIED by user 2026-07-21 & verified — B-038 now balances (brite 0.00, accountedFor 24.5005 vs originalVol 24.5, balanced<0.01, ⚠ flag gone).** B-038 has 0 ingredient commitments (converted batches carry no grain bill), so no commitment refresh needed for the one-off.

Only the PRE-PLANNED path (existing `target_batch_id` created earlier via batches POST with an estimate) drifted.
