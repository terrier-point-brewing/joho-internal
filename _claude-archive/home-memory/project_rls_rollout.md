2026-07-09: Audited RLS on prod Supabase (`drlsazatrcrdwaihjmex`). **Proven live exposure:** 39 of 66 objects on the PostgREST Data API are readable by the public `NEXT_PUBLIC_SUPABASE_ANON_KEY` (ships in browser bundle) — including `payroll_entries`, `payroll_config`, `pay_periods`, `employees` (wages/PII), plus all production/recipe/inventory/supplier data. 27 already locked (profiles, invoices, expenses, system_settings, audit_log, account_requests, events, square_*). Verified by hitting `/rest/v1/<table>` with the anon key.

**Access model (dictates safe approach):** browser client (anon) = auth only (login/logout/set-password), safe. Server client `lib/supabase/server.ts` = anon key + user JWT cookie → runs as `authenticated` role, and directly queries tables in ~85 API routes + a couple server components (`.from(...)`). Admin client `lib/supabase/admin.ts` = service_role, bypasses RLS, used in 46 files. Authz enforced in app layer via `lib/auth.ts` `requireRole`/`getSessionUser`; roles in `profiles`; DB helper `get_my_role()` (SECURITY DEFINER). No per-user row ownership (single-tenant brewery). → **deny-all RLS would break the ~85 authenticated-role routes.**

**Recommended plan:** Phase 1 (Model A, zero app-code change, low risk): `ENABLE RLS` on every exposed base table + `FOR ALL TO authenticated USING(true) WITH CHECK(true)`; tighten payroll_*/employees to manager+admin via `get_my_role()`; anon implicitly denied → closes public hole. `batch_exhaustion` is a VIEW → `SET (security_invoker=true)` not RLS. Phase 2: drop cruft on attack surface — backups `brew_batches_bak_20260704`, `cold_storage_inventory_bak_20260704/07`, and drift tables `workflow_templates`, `workflow_template_steps`, `brew_inventory_adjustments` (drop migrations 20260717/18/20 NOT applied to prod — more drift). Phase 3 (optional hardening, Model B): move server-client data reads to service_role admin client, then drop `authenticated USING(true)` so logged-in users can't bypass app role checks via direct PostgREST.
