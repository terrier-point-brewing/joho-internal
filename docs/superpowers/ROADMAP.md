## Process this project follows (every spec, no exceptions)

1. **Brainstorm**: `Skill(superpowers:brainstorming)`. Explore current state (usually via an `Explore` subagent survey — cheap, thorough, avoids burning controller context on raw file reads). Flag decomposition immediately if a request bundles independent subsystems — most specs on this roadmap started as one larger ask that got split (e.g. Spec 2c split into 2c-1/2c-2; the very first feature request became this entire 7-item roadmap). Ask clarifying questions one at a time, multiple-choice where possible. Present architecture in sections, get approval per section.
2. **Write the spec doc** to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, self-review for placeholders/contradictions/scope, commit it, ask the user to review.
3. **Write the plan**: `Skill(superpowers:writing-plans)`. Read every file the plan will touch in full (current line numbers, current schema) — don't trust prior specs' line-number references, code shifts between specs. Every task needs complete code in the plan text, not prose descriptions. Self-review for spec coverage / placeholders / type consistency across tasks. **Commit the plan file immediately after writing it** — this has been forgotten at least 3 times across this project's history; it's cheap to forget and easy to catch by running `git status` right after `Write`.
4. **Set up an isolated worktree**: `EnterWorktree({name: "<topic>"})`. Immediately `cp .env.local` into it (gitignored, doesn't come over), `npm install`, `npm run build` to confirm a clean baseline. **Then check `git log` in the new worktree against `git log` on `main`** — `EnterWorktree` branches from the last *pushed* state of `main`, so any spec/plan commits made locally but not yet pushed won't be there; fast-forward-merge them in before dispatching any implementer.
5. **Execute via `Skill(superpowers:subagent-driven-development)`**: fresh implementer subagent per task (cheap model for pure-transcription tasks with complete code in the brief, standard model for multi-file integration, never omit the model param). Every dispatch must tell the subagent to verify, before every single write and every commit: `pwd` / `git branch --show-current` shows the worktree branch, **and** that any absolute file path it's about to write contains the worktree's full path segment (e.g. `.claude/worktrees/<name>`) — not just a `cd` check. This exact mistake (subagent writes to/commits on the shared main checkout despite believing it's in the worktree) has happened **at least 4 times** across this project, including to the currently-in-progress 2c-2 session. See Lessons Learned #6.
6. **Review every task**: `scripts/review-package BASE HEAD` then a fresh reviewer subagent, model scaled to risk (cheap for mechanical diffs, standard/capable for business logic). Never skip the loop on a finding — dispatch a fix, re-review, repeat until clean. The highest-risk task in this whole roadmap (Spec 2b's Ship endpoint, a `creditedQty` reconciliation bug) took 3 review rounds to actually close — don't rush approval on arithmetic/financial logic.
7. **Final whole-branch review** on the most capable model available, with the merge-base diff package, before presenting finish options.
8. **`Skill(superpowers:finishing-a-development-branch)`**: build/lint check, present the 4 options, execute the user's choice. This project has always chosen "push + create PR," never direct merge.
9. **After the user confirms the PR merged**: fetch + ff-merge `main` locally, `ExitWorktree({action: "remove"})`, then **independently verify** `git log` on main shows no stray commits from implementer mistakes (this has happened — see #6) before considering the spec truly closed.

## Lessons learned (apply to every future spec on this roadmap)

1. **No test runner exists in this repo.** Verification is always `npm run lint` + `npm run build` + per-task code review + (where it matters) a direct REST API check via `curl` against the live Supabase project using `.env.local`'s `SUPABASE_SERVICE_ROLE_KEY`. Never claim "verified" without one of these forms of evidence.
2. **`npx supabase db push` is unreliable in this repo** — there's a pre-existing mismatch between `supabase_migrations.schema_migrations` (tracks ~90 fine-grained historical timestamps) and this repo's squashed/renamed local migration filenames. **Never run `supabase migration repair --status reverted`** — doing this once deleted all 90 tracking rows and required a manual SQL restore. To apply a new migration: paste its SQL directly into the Supabase Dashboard SQL Editor for project `drlsazatrcrdwaihjmex`, then separately run `insert into supabase_migrations.schema_migrations (version) values ('<8-digit-date-prefix-of-the-migration-filename>') on conflict (version) do nothing;` so the CLI at least tracks new migrations going forward. This requires asking the user to paste SQL into the dashboard themselves and confirm — the agent cannot do this step itself.
3. **Two real, pre-existing infra bugs were found and fixed mid-project, unrelated to any spec's own scope**: (a) `supabase/.temp/` (Supabase CLI's local link cache) had been accidentally committed and needed gitignoring/untracking; (b) migration `20260617_status_history_and_exhaustion.sql` had silently never been applied to the live database (the `batch_exhaustion` view didn't exist), discovered only when Spec 2a's migration tried to depend on it. **Lesson: don't assume a migration file in the repo means it was actually applied — verify against the live schema via REST API before depending on it.**
4. **`EnterWorktree` branches from the last *pushed* state of `main`**, not local HEAD. After writing a spec/plan doc and committing it locally, always check whether the new worktree actually has those commits (`git log` comparison) and fast-forward-merge them in if not. This has been missed at least twice, requiring mid-session recovery.
5. **The plan file itself gets forgotten** (written via the `Write` tool but never `git add`/`git commit`'d) — happened repeatedly. Always `git status` immediately after writing a plan doc.
6. **The single most common and costly mistake**: a subagent (implementer or even the controller itself, once) believes it's writing inside an isolated worktree but is actually writing to the shared main checkout — because it `cd`'d correctly but then passed an absolute path to a file-write tool that was missing the worktree's directory segment, or because (as with the current 2c-2 session) it never actually entered a worktree in the first place despite believing it had. **Mitigation that actually works**: every implementer dispatch must explicitly require checking that the FULL ABSOLUTE PATH about to be written contains the worktree segment, not just running `git branch --show-current` (which can pass while the file write itself still targets the wrong directory if the path was constructed wrong). When this mistake is caught, the fix is: `git cherry-pick <the-commit>` into the correct worktree branch, then `git reset --hard <commit-before-the-mistake>` on `main` — **always get explicit user confirmation before the `reset --hard` on main**, even though the same content now safely exists in the worktree branch.
7. **The preview/browser testing tool's working directory is locked to the main repo root** — it can never render code that exists only in an unmerged worktree. True browser E2E verification of worktree-only code isn't possible before merge. State this limitation honestly in PR descriptions and final reviews rather than implying full E2E coverage occurred.
8. **Production deploys are manual** (`vercel deploy --prod` from repo root, per this repo's `CLAUDE.md`) — merging a PR to `main` does **not** auto-deploy. If "I don't see the new feature in the live app" comes up, check deployment freshness (ask when `vercel deploy --prod` was last run) before assuming a code bug.
9. **Live financial/Square actions are never executed autonomously.** Real Ship/export submissions against real cold-storage inventory, and (coming in Spec 2c-2) real Square refunds, always require explicit, fresh opt-in from the user — a prior verification step approving something similar does not carry forward to a new action.
10. **Always independently re-verify subagent self-reports** (build output, "files match the brief," hand-traced arithmetic) via direct `Bash`/`Read` rather than trusting the narrative — this caught a real, three-rounds-deep arithmetic bug in Spec 2b's Ship endpoint (`creditedQty` summing didn't actually equal the requested quantity; required computing every credit's quantity in one flat pass over the array, by index, *before* any batch-grouping happened, since `Map`-grouped traversal order isn't guaranteed to match the flat array's order when one batch contributes multiple non-adjacent entries).
11. **Cost-basis-locked-at-payment-time is the established convention for anything involving a customer's deposit**: once a deposit is paid, the dollar amount tracks against the percentage *at that moment*, never recomputed from current ingredient costs later — this exact principle is core to Spec 2c-2's refund math and should be checked for consistency in Spec 6 (Commitments invoicing) if it ever needs to reference what a customer was originally quoted/charged.

## Architecture map (for orienting a fresh session quickly)

- **`lib/production/`**: `batchCompletion.ts` (`checkAndCompleteBatch`, Spec 2a), `exciseTax.ts` (`computeExciseTaxBreakdown`, Spec 2a), `commitmentFulfillment.ts` (`checkAndFulfillCommitment`, Spec 2b — gated on batch `status === 'complete'`), `coldStorageDepletion.ts` + `exportBayEquipment.ts` + `exportTransactionWriter.ts` (extracted from Spec 2b's Ship endpoint during Spec 2c-1, shared by both the regular Ship flow and Ad-Hoc Export).
- **API routes**: `app/api/production/export-bay/{ship,ship-adhoc,inventory,active-allocation-check}/route.ts` (Specs 2b/2c-1). `app/api/production/allocations/[id]/route.ts` (pre-existing PATCH, gaining the new `/adjust` sibling endpoint in 2c-2). `app/api/production/allocations/[id]/invoice/route.ts` (pre-existing deposit-invoice generate/send/sync — 2c-2 extends its sync action to capture `square_payment_id`).
- **UI**: `app/production/components/ExportTab.tsx` (the Export section's tab shell — Allocations tab was removed and replaced by Export Bay in Spec 2b), `ExportBayTab.tsx` (the 2-column screen, Specs 2b/2c-1), `BatchLogTab.tsx` (pre-existing batch/allocation list — 2c-2 adds a refund-confirmation modal to its existing inline percentage editor).
- **Square integration**: `lib/square/client.ts` (shared request wrapper), `lib/square/deposit-invoices.ts` (pre-existing, `calculateIngredientDeposit`/`createDepositInvoice`/`publishDepositInvoice`/`reviseDepositInvoice`/`getDepositInvoiceStatus`), `lib/square/refunds.ts` (pre-existing read-only `fetchRefunds`, gaining a `createRefund` write function in 2c-2).
