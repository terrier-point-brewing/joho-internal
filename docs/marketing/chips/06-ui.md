# Chip 6 — Calendar, Compose, entry detail, Accounts

**Read `docs/marketing/CONVENTIONS.md` in full before writing anything**, and then
**read `docs/UI_STANDARD.md` §4 and §5 properly.** This chip is the one where "matches
the rest of the app" is the actual requirement, and this repo is strict about it.

Chips 1–5 are merged: the section and its four scopes, the six `public.marketing_*`
tables, the plugin contract + registry + fake, the worker and retry route, and the
entries/media/accounts API. Chip 7 follows you and re-runs every gate together.

---

## 1. Intent

Marketing is one calendar holding posts, reels, stories and boosts; a robot that
publishes what is on it; later an assistant that proposes entries. **Humans approve —
nothing publishes or spends without a human action.**

You build the surface where that human acts. Everything underneath already works and
is tested; if something here feels like it needs new backend behaviour, **stop and
report** rather than adding it.

## 2. Do not introduce a design language

The functional requirements are in §4. Before you satisfy any of them, **go read how
this app already does the same job** — how Production lays out its calendar, how
Finance builds a side panel, how any section renders a status chip, a form, an empty
state. Reuse those components and those patterns. A Marketing screen that a person
cannot tell apart from a Production screen is the target.

Non-negotiables, all enforced:

- `StickyHeader` holds **title → description → the one subtab bar, and nothing else.** No buttons, no selects, no status text. Page actions go at the top of the scrollable content as `flex justify-end gap-2 mb-4`.
- A page-local view switcher under a real subtab bar is a **`ButtonGroup`**, never a second `TabBar`.
- Buttons are `.btn-primary` / `.btn-secondary` / `.btn-danger`, and **the tier owns its geometry** — overriding padding, height or width is an eslint error. `w-full` is the only exception.
- No raw colors. Semantic tokens only. Status pills are `Badge` with a `tone` from `app/components/ui/tone.ts`; surfaces are `Card`.
- **There is no `warning` colour** in this app. Those tokens do not exist and the classes fail silently. The amber accent box is the house caution pattern.
- Inset bars use `mx-`, never `px-`.
- Feature logic lives in a co-located component, not inlined in `page.tsx`.

## 3. One backend change you do own

`POST /api/marketing/entries` currently **refuses channels unless `postNow` is set**
(`lib/marketing/entries.ts`, the `!input.postNow && channels.length > 0` guard). That
guard existed because attaching deliveries to a draft used to flip its status away
from `draft`. **PR #486 fixed the trigger** — deliveries that are all `pending` now
derive nothing — so the guard is obsolete and is actively in your way.

Replace it: a draft with channels creates its deliveries with `status = 'pending'`,
and the entry stays `draft`. That is how a saved draft remembers which channels a
person picked; without it, Compose's channel selection silently evaporates on save.

Add the test: a draft with two channels persists two pending deliveries **and the
entry is still `draft`** afterwards. Nothing else about the route changes — `postNow`
still creates `scheduled` deliveries and runs the worker inline, and a future
`scheduled_at` is still refused.

## 4. What to build

### Calendar (`/marketing/calendar`, the default subtab)

A time-based view of entries. Week-by-day is the natural shape; look at
`app/production/components/CalendarTab.tsx` first and match how this app already
presents scheduled work. (That file predates the token rewrite and still uses raw
`zinc-*` — **copy its structure, not its colors.**)

- Each entry shows its status and its channels at a glance.
- A **Compose** action, in the scrollable content, not the header.
- A clear, plain state when **no account is connected** — which is the state this ships in, since production registers zero channels. Not an error, not a "should never happen": the ordinary first-run condition, saying what to do about it.
- A **reserved area for band entries** (those with `ends_at` set) that renders empty for now. Nothing creates one yet; the space exists so adding them later is not a re-layout.
- Reads `GET /api/marketing/entries?from=&to=`. The window is half-open.

### Compose

- **Media picker**: upload through `POST /api/marketing/media`, preview, client-side dimension probe. Multiple media, **explicitly orderable**, because order is meaningful and the API preserves exactly what you send.
- **Caption** with a character count.
- **Channel selection driven by the registry** — never a hard-coded list. For each channel call `plugin.validate(entry, media)` and, when it says no, **disable that channel and show the reason next to it**. The reasons are already written as sentences; render them as-is.
- **When**: **Now only.** The date/time control is present and **visibly disabled** — a person should see that scheduling is coming, not wonder where it went.
- Actions: **Save as draft** and **Post now**. **Schedule is present and disabled.**

### Entry detail

Caption, media, and **per-delivery status, error, and external link**. A published
delivery links out to the post; a failed one shows its error and a **Retry** button
wired to `POST /api/marketing/deliveries/[id]/retry`. Retry is gated on
`CAP.marketingPublish` — a person without it should not see a button they cannot use.

### Accounts (`/marketing/accounts`)

A read-only mirror of Settings → Marketing → Connected accounts: per channel, status,
handle. Same data, no controls.

### Settings → Marketing → Connected accounts

A new settings group, registered in `app/settings/nav-config.tsx` following the
existing groups exactly. Per channel: status, handle, and **Connect / Reconnect /
Disconnect**, wired to the accounts routes. Driven by the plugin registry: in dev it
lists the fake channel; **in production it lists nothing**, and that must render as a
sentence explaining there is nothing to connect yet — not as a blank panel.

Gate the group on `CAP.marketingAccountsManage`.

## 5. Gate

There is **no UI test setup in this repo** (`vitest` runs in `node`, no jsdom), so the
browser is the gate. Do not simulate it.

- [ ] `npm run verify`, `npm run check:permissions -- --strict`, `npm run build` — green.
- [ ] Your new route test passes: a draft with channels keeps `status = 'draft'` and gets pending deliveries.
- [ ] **In the browser, signed in** (Claude in Chrome, credentials per the conventions sheet):
      Calendar renders; Compose opens; a media upload previews; the fake channel appears and is **greyed with its reason** when `validate` fails; **Schedule and the date picker are visibly disabled**; Save as draft persists **with its channels** and reopens with them intact; Post now publishes through the fake and the entry moves to `done`; entry detail shows the external link; a forced failure shows the error and **Retry works**.
- [ ] Screenshot every screen: Calendar (populated **and** the no-account state), Compose, entry detail with a published delivery, entry detail with a failed one, Accounts, and the Settings group.
- [ ] Side-by-side check: put a Marketing screen next to an existing Production or Finance screen and confirm they read as the same app. Say what you compared.
- [ ] Delete every row and uploaded object you created. Confirm with counts.
- [ ] **Leave the Chrome tabs open.**

## 6. Do not build

- Any migration or schema change. The trigger is already fixed; if you think you need another, **stop and report**.
- Any change to the worker, the cron, or `vercel.json`.
- A working Schedule, or any path that books a future `scheduled_at`.
- Video handling, transcoding, or thumbnailing.
- Library, Plan, Ads, or Insights subtabs. Two subtabs only.
- Any metrics display or writer — `marketing_metrics` stays empty and unread.
- Any real channel, credential, or network call to a live service.
- Any proposals or assistant affordance. `origin = "assistant"` stays a valid value with no UI.
- Any brand selector or brand scoping.
